How ragevalkit Works

A complete walkthrough of a small Python library that tests chatbots and RAG systems: every file, every major function, and the workflow from serve() to the final score.

Based on ragevalkit v0.1.3 · read from the source code, not run.

1. What it is

ragevalkit is an evaluation tool. You give it one Python function, fn(question) -> answer, which is your chatbot or RAG pipeline. It then does five things:

  1. Takes a list of test questions, each with an expected answer.
  2. Sends every question to your function and records the answer.
  3. Scores each answer with an LLM judge and with text-similarity metrics.
  4. Saves everything to a single JSON file.
  5. Shows trends, scores and per-question detail in a web dashboard, and exports to Excel.

Run it again after you change your pipeline, under a new version name, and you can compare quality over time.

2. The simplest way to use it

import ragevalkit

@ragevalkit.step("retriever")            # optional: records this part of your pipeline
def retrieve(q):
    return vector_db.search(q)

def my_rag(question):
    docs = retrieve(question)
    return llm.generate(question, docs)

ragevalkit.serve(my_rag)                 # opens http://localhost:8001

In the dashboard you upload an Excel or CSV file of test cases, click Run, and watch the progress live. The test file needs five columns:

ColumnMeaning
chat_idGroups turns that belong to one conversation
turn_noOrder of the question inside that conversation
typeFree label, such as rag or conversational
questionWhat is sent to your function
expected_answerThe correct answer, written by a human
expected_sources (optional)Documents your retriever should find

5. Startup: what serve() does

  1. Validates your arguments and raises ConfigError immediately if something is wrong (for example a bad source_check_mode).
  2. Loads .env into the environment, without overwriting existing variables. This is how GROQ_API_KEY or OPENAI_API_KEY reach LiteLLM.
  3. Builds a Config, passing optional values only when you set them explicitly.
  4. Calls create_app(). With eval_env="prod" only /api/health works and everything else returns 503. Otherwise it creates the store and the run manager, mounts the routers and serves the dashboard. Unknown non-API paths return index.html, so refreshing a React page works.
  5. Opens the browser after 1.5 seconds and starts uvicorn on 127.0.0.1.

6. How your function is called

At startup the runner looks once at your function's parameter names (_detect_sig) and decides how to call it for every question:

Your function has a parameter named…The runner
session_id, thread_id, conversation_id…Passes a session ID. Your backend owns the chat history.
history, chat_history, messages…Passes the full history each turn, as dict or openai format.
neitherPasses only the question.

The alias lists are configurable. Async functions work. Whatever you return (string, dict, Pydantic model, object) is turned into a string by _coerce_to_str; for a dict it tries answer, response, output and so on.

7. The life of one evaluation run

Choosing the test data

start_run() runs what you pick in the Execute dialog: groups and/or individually picked test cases, worked out by store.resolve_selection(). A case in several selected groups runs once, and the earlier turns of each chat are added so follow-up questions have their context (you can turn that off). POST /runs/preview returns the exact count first, and two different cases claiming the same chat and turn are reported as a conflict. It can also run an uploaded file (imported into the library as a group first) or the configured default_dataset. It rejects bad version names, and existing ones unless overwrite is set.

The row loop

  • Only one run can be active at a time, otherwise you get RunBusy (HTTP 409).
  • Rows are sorted by chat_id and turn_no, so multi-turn chats replay in order.
  • Each chat gets one session ID (a random UUID, or your session_id_fn) and its own history; each answer is appended for the next turn.
  • After each row a progress event is added to a list; the browser reads that list through a server-sent-events stream.
  • Stop is checked only between rows. The current row finishes, partial results are saved and the status becomes stopped.

8. What happens to every question

Source check

If the test row has expected_sources, the runner compares them with the sources your steps recorded.

  • keyword mode (default): a case-insensitive substring match. | means AND and , means OR, so a.pdf , a_v2.pdf | policy.pdf means (a.pdf or a_v2.pdf) and policy.pdf.
  • llm mode: the judge decides. It ignores extension, folder path and capitalisation, but treats a different year or version as a different document. If the LLM call fails, it falls back to keyword mode.
  • off: skipped.

Scoring

ScoreWhere fromMeaning
answer_marks (0–10)LLM judgeHow well the answer matches the expected answer in facts and intent. Hallucinations are penalised.
material_marks (0–10)LLM judgeWhether the retrieved text contains enough information to answer. null for conversational rows.
keyword_recalllexical.pyShare of the expected answer's keywords found in the generated answer.
bm25_scorelexical.pyBM25 text similarity, normalised to 0–1.
semantic_similaritylexical.pyCosine similarity of sentence embeddings from a local model (all-MiniLM-L6-v2).
your ownextra_metricsAny function (expected, generated) -> float.

The judge response is checked by a Pydantic Grade model, so marks outside 0–10 or malformed JSON are rejected. Failed calls retry with pauses of 2, 4 and 6 seconds, then raise JudgeError. You can replace the judge completely with your own judge_fn.

9. Step recording: watching inside your pipeline

Wrap parts of your pipeline in @step("name") or with step("name") as s:. The library then records how long each part took, what it received and returned, which text it retrieved (s.material, sent to the judge) and which documents it used (s.sources, used by the source check). The dashboard shows per-node timing, so you can see which stage is slow.

  • Zero overhead outside an eval. Steps do nothing unless a question is being run, so the decorators are safe to leave in production code.
  • A recorder per question, not per thread. The runner handles one question at a time, so everything recorded while your function runs belongs to that question, even from a thread pool or executor you start. Each step takes hold of its question's recorder when it starts, and a closed recorder ignores late steps, so a slow thread from one question cannot leak into the next. Steps are listed in the order they started.
  • Material is declared. Only a step that sets s.material, or is decorated with material=True, supplies the retrieved text the judge reads. If none declares it, decorated outputs are used as before and a warning says how to be explicit. Material is cut at max_material_chars (20,000) and displayed values at max_step_value_chars (1,000), each with a marker saying how much was left out.
  • Repeated steps add up. A step that runs several times has its times summed in node_timings.
  • Always cleaned up. _deactivate() sits in a finally block, so one failed question cannot leak steps into the next.
  • Secrets hidden. Inputs whose name contains password, token, key, secret and similar are stored as [REDACTED].
record_detailStored per step
all (default)Inputs, outputs, material, sources and timing
selectedOnly steps where you set .material or .sources yourself
offName and time only

10. Storage: one JSON file

store.py uses TinyDB, so everything lives in one readable JSON file (eval_store.json by default). No database server, no migrations.

  • Two result tables. The dashboard list only needs the small runs table. The big receipts table is read only when you open a version or download it.
  • Stable test-case IDs. tc_id is a hash of chat_id|turn_no|question, so re-importing the same question gives the same ID. Editing a case adds a new version row and keeps the old ones; the tc_id follows the case when its chat or turn is edited.
  • Per-case scores. Each run saves a score per test case (case_scores, keyed by a hash of chat, turn, question and expected answer). That is how versions that ran different test cases are still compared fairly, on the cases they share.
  • Groups are labels. A case can carry any number of them, and a receipt remembers the labels it ran under, so history survives later changes.
  • Deleting. A test case is removed for good (all versions and labels); old receipts keep their own copy of the question and answer and are marked as deleted. A group is only hidden (deleted_at) so it can be restored. A version is removed for good.
  • Excel export. export_xlsx() writes a Summary sheet and a Results sheet with readable column order, wrapped text and coloured headers.
  • Thread safety. One lock protects all access, because the runner thread, the generator threads and the web threads share the file.

11. Login and the REST API

Login

  1. users is a string like "alice:pw1,bob:pw2" (default admin:admin123).
  2. The password is compared in constant time.
  3. A session token is base64(user + expiry) plus an HMAC-SHA256 signature, sent in an httponly cookie that lasts 12 hours.
  4. With require_login=False, any username is accepted as a guest.

13. Things worth knowing

The recommendation works on shared test cases. recommend.py compares versions on the cases they all ran, using answer_weight, material_weight, recommendation_tolerance and max_response_time from serve(). A version that shares too little with the others (under half a typical version's size), was stopped early, or failed on a shared case is left out, and the dashboard says why.

The summary is checked. The AI findings must pair every watch-out with a suggestion. A reply that does not is sent back with the reason; a watch-out still left without a suggestion gets one written from the run's own numbers.

Dependencies are pinned for safety. LiteLLM is limited to >=1.104,<1.107; version 1.107.0 and 1.82.7 / 1.82.8 were published with malware.

eval_env="uat" only logs a line. Comments in config.py mention an /api/uat/ask endpoint, and that route does not exist.

judge_fn still needs an LLM key for the summary. The end-of-run findings always call the judge model. Without a key it retries, then saves "Summary could not be generated for this run".

The document text goes to a model. Generating test cases sends your documents' text to generator_model (default: the judge model). Pick one you are allowed to send them to, such as a local ollama/... model.

Limits. Run progress lives in memory only (finished results and saved generation batches survive a restart, a run in progress does not). The server binds to 127.0.0.1, so other machines cannot reach it. Only one run can be active at a time.

14. Summary

ragevalkit is small and self-contained. serve(fn) starts a FastAPI server. A background thread replays your test questions through fn, while @step quietly records the pipeline internals. Each answer is scored by an LLM judge plus three text metrics, and the results land in one JSON file and a React dashboard. Everything else (login, groups, importing and generating test cases, versioned test cases, the shipping recommendation, Excel export, hooks) exists to make that loop easy to repeat after every change to your RAG system.
