ragevalkit

Evaluate any RAG pipeline or LLM chatbot version-by-version, with an LLM judge, lexical metrics, a React dashboard, and zero-setup persistence.

Installation

Install directly from GitHub. No PyPI package yet. Install the latest, or pin a release tag (v0.1.0 to v0.1.3) for repeatable installs. Document-based test case generation, bulk import and the paired findings are newer than v0.1.3, so use the latest until the next tag.

Direct install
pip install git+https://github.com/devanshmakam-youngsoft/ragevalkit.git
In requirements.txt
git+https://github.com/devanshmakam-youngsoft/ragevalkit.git
ℹ️

Run pip install -r requirements.txt from Git Bash on Windows if git is not in your PowerShell PATH.

ℹ️

Dependencies are pinned for safety. litellm is held to >=1.104,<1.107 because 1.107.0 (21 Oct 2026) and 1.82.7 / 1.82.8 (Mar 2026) shipped credential-stealing malware. Raise the upper bound only after checking that a newer release is clean.

Quick start

Pass your RAG function to serve(). ragevalkit wraps it, runs the eval engine, and opens the dashboard.

import ragevalkit

# Your RAG function — any of these signatures work
def my_rag(question: str) -> str:
    return pipeline.run(question)

ragevalkit.serve(my_rag)

The dashboard opens at http://localhost:8001. Add test cases, run evaluations, and compare versions — all from the UI.

Minimal real example
import ragevalkit

def my_rag(question: str, session_id: str = "") -> str:
    result = backend.chat(session_id, question)
    return result["answer"]

ragevalkit.serve(
    my_rag,
    port=8002,
    store_path="eval_store.json",
    judge_model="groq/llama-3.3-70b-versatile",
    require_login=False,
)

Pipeline function

ragevalkit inspects your function's parameter names at startup and adapts automatically — no config needed for the common cases.

Accepted signatures
SignatureModeHow it runs
fn(question) stateless Runner calls with the question only. No history passed.
fn(question, history) stateless Runner builds and passes the full conversation history each turn. Use history_format="openai" for OpenAI message format.
fn(question, session_id) stateful Runner passes a session token; your backend manages history. Each chat_id gets a fresh session.
Return value

Return a str, a dict (ragevalkit finds the answer via answer_keys), or a Pydantic model. Async functions work too.

# All of these work
return "The answer is..."
return {"answer": "The answer", "sources": [...]}
return MyResponseModel(answer="The answer")
Custom parameter names
# If your function uses non-standard param names
ragevalkit.serve(
    my_rag,
    session_params=["thread_id", "conversation_id"],
    history_params=["chat_history", "messages"],
    history_format="openai",  # or "dict" (default)
    answer_keys=["response", "output", "answer"],
)

Step recording

@ragevalkit.step("name") instruments any function in your pipeline. Steps record timing, inputs/outputs, retrieved material, and sources — all visible per-question in the dashboard. Steps are zero-overhead outside eval runs.

As a decorator
import ragevalkit

# Timing + inputs + output captured automatically
@ragevalkit.step("analysis")
def analyse(question, history):
    ...

@ragevalkit.step("rerank")
def rerank(query, docs):
    ...

@ragevalkit.step("generation")
def generate(question, context):
    ...
As a context manager — set material and sources

Use this form when you need to explicitly set .material (the retrieved context sent to the judge) and .sources.

with ragevalkit.step("retrieval") as s:
    docs = vector_db.search(query)
    s.material = "\n\n".join(d.text for d in docs)
    s.sources  = [d.id for d in docs]
Which step supplies the retrieved text

Only a step that declares its material feeds the judge's context score. Declare it with s.material = … in the with form, or decorate a function that returns the text with material=True. Other steps (a rewrite, the LLM call) are timed but their output is not treated as retrieved context.

@ragevalkit.step("retrieval", material=True)   # the return value is the retrieved text
def retrieve(query):
    return "\n\n".join(d.text for d in vector_db.search(query))

If no step declares anything, the output of decorated steps is used as before and the server log warns, with the fix. Material is cut at max_material_chars (20,000) and shown inputs, outputs and notes at max_step_value_chars (1,000); a cut ends with "… (+N more characters)", and a long list of numbers such as an embedding is shown as [N numbers].

Threads and repeated steps

Steps and notes are recorded for the question being evaluated, whichever thread runs them, so a thread pool or executor inside your function is fine. Steps are listed in the order they started. A step that runs more than once (an agent calling a tool in a loop, or the same search on two indexes in parallel) has its times added up; steps that overlap can therefore add up to more than the response time, which the timing bar notes.

What steps capture
FieldHow setUsed for
elapsedAlways, automaticallyPer-node timing bar in dashboard
inputsDecorator only (auto)Input args visible in receipt
outputDecorator only (auto)Return value visible in receipt
materialExplicit s.material = …, or @step(…, material=True)Retrieved context → sent to judge
sourcesExplicit s.sources = […]Source list in dashboard receipt
record_detail modes
ModeWhat's captured
"all" defaultEverything: inputs, outputs, material, sources, timing.
"selected"Only steps that declare material or sources (s.material, s.sources or material=True) are recorded; other steps are left out entirely, timing included.
"off"Step name + timing only. No content captured.
💡

You do not need record_detail="selected" to keep other steps out of the judge's context: only the step that declares its material supplies it, and every step still shows in the timing bar.

Notes — ragevalkit.note()

Attach free-form metadata to the current question's result. Visible as flags on each row in the dashboard.

# Inside your pipeline function, during an eval run
ragevalkit.note("intent", "billing_query")
ragevalkit.note("difficulty", "hard")
ragevalkit.note("sub_queries", str(len(sub_queries)))

No-op when called outside an active eval run. Secret key names (containing "password", "token", "key", etc.) are silently dropped.

Judge configuration

The judge scores each answer 0–10 for answer quality and retrieved material quality. Uses any LiteLLM model — configure with the matching API key in your .env.

Model
ParameterDefaultDescription
judge_model"groq/openai/gpt-oss-120b"Any LiteLLM model string. Examples below.
judge_api_keyNoneExplicit API key. If omitted, LiteLLM reads GROQ_API_KEY, OPENAI_API_KEY, etc. from env.
judge_retries3Retries on transient LLM failures before a row is marked failed.
generator_modelNoneLiteLLM model that writes test cases from uploaded documents (Test Cases → Generate from documents). Defaults to judge_model. The text of your documents is sent to it, so pick one you are allowed to send them to (a local ollama/… model works).
 
# Model examples (set matching env var)
judge_model="groq/llama-3.3-70b-versatile"    # GROQ_API_KEY
judge_model="openai/gpt-4o"                    # OPENAI_API_KEY
judge_model="gemini/gemini-1.5-pro"            # GEMINI_API_KEY
judge_model="ollama/llama3"                    # no key needed
Custom judge function

Replace the LLM judge entirely with your own scoring logic.

def my_judge(question, expected, generated, material) -> dict:
    score = compute_my_score(expected, generated)
    return {
        "answer_marks":    score,
        "answer_comment":  "Custom score",
        "material_marks":  None,  # optional
    }

ragevalkit.serve(my_rag, judge_fn=my_judge)
Custom judge prompt
ragevalkit.serve(
    my_rag,
    judge_prompt="""
    You are evaluating a customer support chatbot.
    Score answer quality 0-10 based on accuracy and tone.
    Respond with JSON: {"answer_marks": N, "answer_comment": "..."}
    """,
)

Metrics

Built-in metrics run automatically on non-conversational rows. Add custom metrics alongside them.

ParameterDefaultDescription
run_keyword_recallTrueKeyword recall: fraction of expected-answer keywords found in the generated answer.
run_bm25TrueBM25 lexical similarity between expected and generated answer.
run_semantic_similarityTrueCosine similarity via a local sentence-transformers model.
embedding_model"all-MiniLM-L6-v2"Sentence-transformers model for semantic similarity. Downloaded on first use.
extra_metricsNoneDict of {name: fn(expected, generated) → float} for custom scores.
Custom metrics example
import rouge

ragevalkit.serve(
    my_rag,
    extra_metrics={
        "rouge_1": lambda exp, gen: rouge.score(exp, gen)["rouge1"].fmeasure,
        "length_ratio": lambda exp, gen: len(gen) / max(len(exp), 1),
    }
)

Test cases & groups

Everything about test cases is done from the Test Cases page of the dashboard. It has two tabs: All test cases and Groups.

1
Add test cases
Three ways, all on All test cases: + New test case for one, Import for an Excel / CSV file or rows pasted from a spreadsheet, and Generate from documents to have them written from your own PDF, Word, TXT or Markdown files.
2
Organise into groups
A group is just a label (e.g. "billing", "greetings"). A test case can carry any number of labels. Create groups on the Groups tab, tick rows and choose Add to group…, or open a group and use Add test cases to add existing cases or create a new one in it.
3
Run groups and/or picked cases
The Execute dialog takes any number of groups and any hand-picked test cases. A case in several selected groups runs once. Follow-up turns need the turns before them, so a run also includes the earlier turns of each selected conversation (you can turn this off); the dialog shows exactly how many cases will run.
Importing in bulk

Three steps: pick the file, check what will happen, choose where the cases go. Nothing is saved until the last step. The check shows how many rows are new, will be updated, are already there, or cannot be imported (with the row number and reason; a turn of "abc" is reported, not turned into 1).

  • Only the question column is required. Without chat_id each question is its own chat; without turn_no turns are numbered in file order within each chat. Common header names (query, gold_answer, tags…) are recognised and the dialog lets you point any column at the right field.
  • Groups are optional. Pick groups for the whole file, and/or add a groups column (Billing; Refunds) to label rows individually. Missing groups are created.
  • Safe to repeat: importing the same file again changes nothing; an edited answer becomes a new version of the same case. Rows that could not be imported can be downloaded with the reason next to each. A template is available in the dialog.
Generating from documents

Upload up to 5 files (50 MB each). By default 3 questions are written in each of four categories, each category becoming a group:

CategoryWhat it is
DirectThe answer is stated plainly in one place.
IndirectThe answer is in the document, but the question uses everyday words or describes a situation.
Multi-partOne question with several parts answered from different places.
Multi-turnA short conversation. Each follow-up refers back to the earlier answer ("and what if I miss that?") and cannot be understood alone; what it builds on is shown during review.
  • Evidence. The writer sees each passage as numbered sentences and cites the ones that prove its answer; the document's own wording is stored with file and page. A question whose evidence does not point at real sentences is rejected and rewritten.
  • Saved as it goes, approved by you. Questions are saved on the server while they are written, so closing the browser loses nothing. They become test cases only when you press Add; anything not added within 24 hours (batch_ttl_hours) is deleted. Nothing of the upload itself is kept.
  • The model is generator_model (defaults to judge_model).
Types and deleting
  • Type is rag (default: the answer must come from your documents, so retrieved context is scored too) or non-rag (greetings and small talk: graded on the answer only, like conversational). Older values such as query keep working and count as rag.
  • Deleting a test case removes it for good, with its versions and group labels. Past versions keep their own copy of the question and answer and mark the row Test case deleted. Deleting a group only hides it (restore it from Deleted groups). Deleting a version removes it for good. To keep a case but stop running it, mark it inactive.
💡

Columns: question (required), expected_answer, chat_id (groups the turns of one conversation), turn_no, type, expected_sources, groups.

Running evaluations

Start a run from the Execute button on the dashboard.

1
Enter a version name
Type a version name like v1, v2, or a descriptive label. Each version is compared independently in the dashboard.
2
Select test case groups
Check one or more groups. All groups are pre-selected by default. The total case count is shown before you confirm.
3
Add a run note (optional)
Describe what changed — model, prompt, retrieval config. Shown on the dashboard for each version.
4
Run & watch live progress
The dashboard streams progress via SSE. Completed rows show scores in real time. A running version appears as "In progress".
Dashboard features per version
FeatureWhat you see
RecommendationThe version to ship, worked out on the test cases the compared versions share: overall score = answer and context quality weighted by answer_weight / material_weight; versions within recommendation_tolerance of the best are tied and the fastest wins. Archived, stopped or failed versions are left out, and the card says what it was compared on when versions ran different cases.
Quality trend / timeAverage answer and context quality per version, and the time of each step, with the latest version's figures beside each title.
How answers scoredOne bar splitting the questions into Strong (8–10), Fair (5–7) and Weak (0–4), with counts and percentages.
Timing of stepsOne bar of each step's share of the whole response time, from @ragevalkit.step. Time outside any step shows as "Not in a step"; steps that run at the same time can add up to more than 100%.
Watch-outs & suggestionsAI-written findings: each watch-out is paired with the suggestion that answers it. summary_prompt changes what they look for.
Scores by groupAverage answer quality, context quality and response time per group. A case in several groups counts in each.
Results tableEvery question with its answer, scores, groups and time; filter by score tier, group or type, with averages for what is shown. Rows whose test case was deleted since say so.
Run notesThe note you entered at run time, shown under the version name.

Excel export

Download a full .xlsx report from any version's detail view. Two sheets.

SheetContents
Summary Version name, date, notes, groups, total questions, average answer marks, average material marks, average scores per lexical metric, and the LLM run comment.
Results One row per question: ID, question, expected answer, generated answer, answer marks, answer remarks, material marks, material remarks, retrieved context, sources, all lexical metrics, per-node timings, and any extra metadata columns.
ℹ️

The Results sheet is styled: teal header row, text wrap on long columns, auto column widths. Ready to share with stakeholders.

Hooks

on_complete — called after every run
def notify(summary: dict, rows: list[dict]) -> None:
    print(
        f"Run {summary['version']} done — "
        f"avg answer: {summary.get('avg_answer_marks')}"
    )
    # send Slack message, write to DB, trigger CI, etc.

ragevalkit.serve(my_rag, on_complete=notify)
session_id_fn — deterministic session IDs

By default each eval question gets a random UUID session. Supply a deterministic function to replay multi-turn conversations with the same session against a stateful backend.

ragevalkit.serve(
    my_rag,
    session_id_fn=lambda chat_id: f"eval-{chat_id}",
)
