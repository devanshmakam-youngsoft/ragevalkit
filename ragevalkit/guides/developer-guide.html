ragevalkit
version 0.1.3

Measure your assistant, version by version.

ragevalkit replays your test questions through your own function, grades every answer, and shows which version of your pipeline is the one to ship. This guide takes you from the first run to your own judge, with code you can copy.

What you get

Three things happen when you press Execute session.

Your functionragevalkit calls it once per test question, in order, like a real user would.
→
GradingAn AI judge scores each answer and the text your pipeline retrieved. Text metrics run alongside.
→
ComparisonEvery run is saved as a version, so you can see what got better and which one to ship.
→
DashboardScores, step timings, findings with suggestions, every answer, an Excel export.

Your pipeline code stays as it is. You add a small entry file that calls serve(your_function); the production app never imports ragevalkit unless you choose to record steps.

Quick start

Five minutes, no database, no extra services.

1. Install

pip install git+https://github.com/devanshmakam-youngsoft/ragevalkit.git

Put the key of the AI model that will judge your answers in a .env file next to your script (ragevalkit reads it for you). For the default judge that is GROQ_API_KEY; any LiteLLM provider works, and you can skip the AI judge entirely.

2. Serve your function

Create eval_entry.py beside your pipeline. Any function that turns a question into an answer works:

import ragevalkit
from my_app import answer_question          # your existing pipeline

ragevalkit.serve(answer_question, port=8002, require_login=False)
python eval_entry.py

The dashboard opens at http://localhost:8002. Without require_login=False the sign-in is admin / admin123 (change it with users=).

3. Add test cases and run

  1. Open Test Cases. Add a case with + New test case, bring many in with Import (Excel, CSV or pasted rows), or let ragevalkit write them from your own documents with Generate from documents.
  2. Click Execute session, name the version (1, v2, rerank-on…), pick the groups or cases to run, and start.
  3. When it finishes, open the version for scores, step timings, findings with suggestions, and every question's answer.
Tip

Keep evaluation in its own entry file. Your production API keeps running exactly as before, and step() and note() inside your pipeline do nothing outside an evaluation.

Connect your function

ragevalkit looks at the parameter names of your function to decide what to pass. There are three shapes.

Every question is answered on its own. The simplest shape, and right for single-turn pipelines.

Your chatbot is stateless: it rebuilds the prompt from the earlier turns each time. ragevalkit keeps the conversation of each chat_id and hands you the earlier turns as history (empty on the first turn).

Your backend is stateful: it remembers the conversation itself. ragevalkit passes one session id per chat, the same for every turn of that chat and different for the next.

How ragevalkit chooses

If a parameter is named…ragevalkit passes…
session_id, session, thread_id, conversation_id, user_idthe session id of the chat (shape 3)
history, chat_history, messages, conversation, turns, contextthe earlier turns (shape 2)
anything elsenothing: the first parameter is always the question

If a function has both kinds, the session id wins. Other parameters need a default value, because ragevalkit only passes the question and one extra.

Good to know

A parameter called context is treated as history. If yours means something else, rename it, or list your own names with history_params=[…].

Other things your function can do

Return a dictionary or a Pydantic model, be async, use your own parameter names, or receive the history as chat messages.

The keys tried for the answer, in order, are answer, response, output, result, text, content, message, generated_text, generation, completion. Use answer_keys=[…] to add your own.

Evaluate a bot that is already deployed

No access to its code? Your function can simply call it over HTTP, and ragevalkit scores whatever comes back.

Record what happens inside

Scoring only the final answer tells you that a version got better, not why. Recording steps tells you where the time goes, what was retrieved, and which documents were used.

Mark the stages of your pipeline (search, re-rank, the model call…) and ragevalkit shows, for every question:

  • How long each step took, as the “where the time goes” bar on the version page.
  • The retrieved text, which the judge scores as context quality.
  • The documents used, checked against the sources you expected.
  • Notes you attach: intent, tool called, difficulty… anything you want next to the question.

Which one should I use?

  • Use with for the retrieval step whenever you want a source check, and for anything that is only part of a function. You decide exactly what counts as material and sources.
  • Use a decorator when a function already is one clear stage and returns what you would call its result. Inputs and output show up in the step details with no extra code, which is handy when you are tracking down a wrong answer.
  • Mix them freely. A pipeline can use decorators for the model call and a with block for the search.

Say which step retrieved the text

The judge reads only the steps that declare material: a with block that sets s.material, or a decorator with material=True. Steps that do not declare it are timing only, which is exactly what you want for a re-ranker or the model call.

Tip: declare it once

If several steps set s.material, the judge reads all of them one after another: routing details, search settings and the context, sometimes the same context twice. Context quality then looks lower than it is. Let one step (the retrieval) declare the material and keep the others timing-only. Put details you still want to see in ragevalkit.note(…).

Sources work the same way: the sources of every step are put together (each document once), so report them in the retrieval step only. If no step declares material, ragevalkit falls back to the output of decorated steps and writes a warning to the log that says how to be precise.

Notes

ragevalkit.note("intent", "billing") attaches a short fact to the question being evaluated. It appears beside the question in the results. Names such as password, token or api_key are never stored.

What you can rely on

  • Nothing happens in production. Outside an evaluation, step() and note() record nothing and add almost no overhead, so the same code can ship.
  • Secrets stay out. Decorated functions record their arguments, and any argument named like a secret is shown as [REDACTED].
  • Long values are shortened with a marker saying how much was left out (step_value_chars, default 1000; the judge reads up to material_chars, default 20000).
  • Less detail on request. record_detail="selected" keeps only steps that set material or sources; "off" keeps names and timings; record_mode="off" records no steps at all.

LangGraph, agents and threads

Steps belong to the question being evaluated, not to the place they are written. Whichever node, thread or async task runs your code, the step lands on the right question.

That means all of these work, and the example below uses the first three:

  • a node that calls a decorated function (the decorator records the call wherever it is made from);
  • a node with a with block inside it;
  • a decorator on the node itself, including nodes that take a LangGraph config parameter;
  • nodes that run in parallel, async nodes (ainvoke), and steps started from a thread pool.

The version page then shows rewrite, retrieval and llm with their times, the retrieved text and the source refunds.pdf. We ran this exact file, plus variants with parallel branches and async nodes, while writing this guide.

Good to know

A decorated node returns a state update such as {"docs": […]}, so with material=True the material would be that dictionary as text. For the node that does retrieval, a with block lets you set clean material and sources.

Steps that run in parallel each report their own time, so together they can add up to more than the question's response time. That is expected.

A bot with no retrieval

Greeting bots, small talk and tool agents have no “retrieved context” to score. Tell ragevalkit, and they are graded on the answer alone.

  1. Mark the test cases non-rag (a type column when importing, or the type box on a test case). Their context quality is then left out instead of scored as 0.
  2. Do not declare material in your steps. Tool calls and intent checks are timing-only steps.
  3. Set material_weight=0 so the recommendation looks at answer quality only.
  4. Write the expected answer as a behaviour when exact words do not matter: “Greets the user politely and offers help”, “States that order A100 has shipped”. The judge grades the behaviour.

Notes such as intent and tool_called appear beside each question, which makes it easy to see which tool a wrong answer used.

An agent that calls tools in a loop

The model asks for a tool, gets the result, and decides again. Two things are worth knowing: a step that runs several times has its times added up (the llm step below runs once per loop), and when the tool results are how the agent gets its facts, declaring them as material lets the judge check that the answer is supported by them.

Test cases

A test case is a question, the answer you expect, and where it sits in a conversation.

ColumnMeaning

expected_answerWhat a good answer says. Wording can differ; the judge compares meaning.
chat_id, turn_noCases with the same chat_id form one conversation, replayed in turn_no order. Leave them out and every question is its own chat.

Checking that the right documents were retrieved

Report the documents your retrieval step used with s.sources and list the expected ones in expected_sources. ragevalkit compares them and shows what was found and what is missing.

  • Import takes Excel, CSV or pasted rows, shows what will be added, updated or skipped before saving anything, and returns the rows it could not use so you can fix and re-import. Importing the same file twice changes nothing.
  • Groups are labels. Run one group, several, or hand-picked cases. A case in two selected groups runs once.
  • Generate from documents writes questions from your PDF, Word, text or Markdown files (up to 5 files of 50 MB). Each answer comes with the sentences of the document that prove it, and nothing is added until you review and press Add. The text of the documents goes to the model you set with generator_model; a local ollama/… model keeps it on your machine.
  • A conversation’s later turns need the earlier ones, so by default a run also includes the earlier turns of each case you picked. You can switch that off in the Execute dialog.
  • Your own column names? column_map={"user_query": "question", "gold_answer": "expected_answer"}. Example below.

Your own judge

Three levels, from a different model to no AI at all.

Level 1: another model

judge_model takes any LiteLLM model name, with its key in .env or judge_api_key=: "openai/gpt-4o-mini", "gemini/gemini-1.5-pro", "groq/llama-3.3-70b-versatile", "ollama/llama3".

Level 2: your own rubric

Keep the AI judge but tell it how your answers should be graded. Describe only the grading: ragevalkit adds the reply format itself. summary_prompt does the same for the written findings.

Level 3: your own function

For exact checks, rules, a JSON schema, or your own scoring service, replace the AI judge with a function. It receives the question, the expected answer, the generated answer and the retrieved material, and returns answer_marks (0–10) with an optional comment, plus material_marks if you grade the context too.

Good to know

The written findings at the end of a run are produced by the judge model even when you use judge_fn. Without a key for it the run still finishes and the version says the findings could not be written.

Extra scores and hooks

Add your own metrics, carry your own spreadsheet columns, and react when a run finishes.

  • extra_metrics: each function gets (expected_answer, generated_answer) and returns a number. A metric that fails on a question is reported as a problem and the run goes on.
  • on_complete: called once when a run ends, with the summary and the rows (None instead of a summary if the run failed). Post to Slack, fail a CI job, write to a database.
  • session_id_fn: choose the session id sent for each chat, for example to replay a conversation against a stateful backend with a stable id.
  • conversational_types: row types that skip context scoring and text metrics, besides non-rag.
  • source_check_mode: "keyword" (default, ignores path and extension, ignores case), "llm" (tolerates different spellings of a name) or "off".

Running it for your team

  • Sign-in. users="alice:pw1,bob:pw2" sets the accounts. Sessions last 12 hours; set secret= to a fixed value if people should stay signed in across restarts. require_login=False skips the sign-in for local work.
  • Data. Everything is in one JSON file (store_path, default eval_store.json). Copy it to back it up or move it to another machine.
  • Logs. eval_logs/ sits beside it: server.log, one file per run in runs/, one per generation in generation/, each with full details. log_dir= moves them. Keys and passwords are hidden before anything is written.
  • Production safety. eval_env="prod" turns the dashboard and every evaluation route off; only /api/health answers.
  • This guide. It is on by default. show_guide=False hides the Help link and stops serving the guide.
  • Versions. Give every release its own version name, and run the same test cases each time. Pin ragevalkit to a tag in requirements.txt (…ragevalkit.git@<tag>) so everyone evaluates with the same code.

When something looks off

Start with the Problems during this run box on the version page: it says what went wrong in plain words, and Show technical details gives the error. The full log is the Download log button, or eval_logs/runs/. Then look for your symptom here.

Every question says “No answer: the assistant returned an error”

Your function raised an error. The run itself is fine: ragevalkit marks the question failed, records why, and carries on.

Do: open Problems during this run and Show technical details; the last lines name the error. Call your function by hand with one of the questions. Common causes: a key your own pipeline needs is missing from .env, a file path that only works from another folder, the vector index was not loaded before serve() (load it first, as your app does at start-up), or the function needs a second argument that has no default.

“The question was answered, but the AI judge could not grade it”

The judge model did not answer. The usual reasons are shown in the message: a missing or wrong API key, a model name that does not exist, a rate limit, or no network.

Do: put the provider’s key in .env (GROQ_API_KEY, OPENAI_API_KEY…) or pass judge_api_key=; write the model as provider/model; for a rate limit, wait a minute or run fewer questions. Or use your own judge function, which needs no model.

“The AI could not write the findings for this run”

The findings come from the judge model, even when you use judge_fn.

Do: the same checks as above (key, model name, network). The scores and every answer are saved; only the written findings are missing.

Context quality is blank or very low

No step declared the retrieved text, or the case type says no retrieval is expected.

Do: in your retrieval step set s.material = … (or use @ragevalkit.step("retrieval", material=True)). If the bot has no retrieval, mark the cases non-rag and use material_weight=0. See Say which step retrieved the text.

Context quality is lower than the retrieval deserves

More than one step declares material, so the judge reads routing details, search settings or the same text twice, and the end can be cut off at material_chars.

Do: open a question’s Retrieved text and check it holds only the passages. Let one step declare the material; keep the other steps timing-only and put their details in ragevalkit.note().

The step-time bar only shows “Not in a step”

No step ran during the questions, or recording was reduced.

Do: check that your pipeline calls ragevalkit.step(…) on the path the questions take; check record_mode is not "off"; with record_detail="selected" only steps that set material or sources are kept.

Step times add up to more than the response time

One step sits inside another (the outer one includes the inner one’s time), or steps run in parallel.

Do: for nesting, make the steps follow each other instead of wrapping each other. Parallel steps are expected to overlap.

Sources say “not checked”, or “some missing” when they were found

Not checked: the test case has no expected_sources, source_check_mode is "off", or no step reported sources. Missing although retrieved: the names differ.

Do: report sources with a with block and s.sources = […] (decorators cannot report them). Compare the names the step reported with expected_sources; the keyword check ignores case, folders and file extensions, so docs/Refunds.pdf matches refunds. Different spellings of the same document? Try source_check_mode="llm".

A step shows no inputs or output

Inputs and outputs are recorded only for decorated functions.

Do: use the decorator for that step, or record what you need with ragevalkit.note(). Arguments named like secrets show as [REDACTED] on purpose.

“Another evaluation is already running”

One evaluation runs at a time.

Do: wait for it, or press Stop on the version in progress; a stopped run keeps its partial results.

“Version … already exists” or “Version may only contain letters, digits…”

Version names are unique, and use letters, digits, ., _ or - (up to 20 characters).

Do: choose a new name, or tick the option to replace the existing version.

“No runnable test cases in the selection”

The groups you picked are empty, or their cases are all inactive.

Do: add cases to the group, or mark them active. The Execute dialog shows how many cases will run before you start.

A function with a parameter called context or user_id gets the wrong thing

Those names are on the lists ragevalkit uses to recognise history and session parameters.

Do: rename the parameter, or set history_params=[…] and session_params=[…] to your own names. See Connect your function.

The answer shows as a dictionary or object text instead of the answer

Your function returned a dictionary or object, and none of its keys is a known answer key.

Do: return a string, or add your key with answer_keys=["my_key"].

I cannot sign in, or I am signed out after a restart

The default account is admin / admin123 unless you set users=. Without a fixed secret= a new one is made on every start, which ends existing sessions.

Do: set users= and secret=, or require_login=False locally.

“Missing required column(s)” when importing

The file does not have the columns the older dataset upload needs.

Do: use Test Cases → Import, which only needs a question column and lets you pick which column is which; or add column_map= to serve().

Generating test cases: “has no selectable text”, “password-protected” or “old Word files”

The file cannot be read as text: a scanned PDF, a protected file, or a .doc.

Do: upload a text-based PDF, remove the password, or save .doc files as .docx. Plain .txt and .md always work.

The dashboard looks old after an update, or a new option is not recognised

The environment still has the previous version of ragevalkit, or the browser kept the old page.

Do: reinstall with pip install --force-reinstall --no-deps git+https://github.com/devanshmakam-youngsoft/ragevalkit.git, then refresh the page with Ctrl+F5.

“Address already in use”, or the page does not open

Another program is using the port, or the browser did not start.

Do: pick another one with port=8003 and open http://localhost:8003 yourself.

“Semantic similarity failed” in the problems list

The small local model for the “meaning” score could not load, usually the first time on a machine with no internet.

Do: connect once so it can download, or set run_semantic_similarity=False. All other scores are unaffected.

Where are the logs, and what should I send when asking for help?

Do: on the version page press Download log, or open eval_logs/runs/ next to your eval_store.json. For an error outside a run (a message with a reference number), search eval_logs/server.log for that reference. Keys and passwords are already hidden.

Source verification

ParameterDefaultWhat it does
source_check_mode"keyword"

How to verify retrieved sources against expected_sources in the dataset. "keyword" (default) uses substring matching — separate AND-groups with | and OR-alternatives within a group with , (e.g. "doc_a | doc_b.pdf,doc_c" requires doc_a AND either doc_b or doc_c). "llm" uses the judge model for fuzzy / alias-tolerant matching. "off" disables source verification entirely.

Hooks

ParameterDefaultWhat it does
on_completeNone

Called once after a run finishes (success or failure)::

def on_complete(summary: dict, rows: list[dict]) -> None:
    send_slack_notification(summary)
session_id_fnNone

Returns the session ID for a given chat_id. Defaults to uuid.uuid4(). Supply a deterministic function to replay conversations with the same session against a stateful backend::

session_id_fn=lambda chat_id: f"eval-{chat_id}"
summary_promptNone

Override the system prompt used by the LLM to write the run's "pitfalls and suggestions" shown in the dashboard. The required JSON reply format is appended automatically, so only describe what to look for and the tone.

Good to know

  • One evaluation runs at a time. Finished results are saved as they complete. A run that is in progress lives in the running server, so if the server is restarted, start that version again.
  • The dashboard is served on this computer (127.0.0.1). To share it with a team, run it on a shared machine behind your usual network setup, with sign-in on.
  • Documents sent to a model. Generating test cases sends the text of your documents to generator_model (the judge model by default). Choose one you are comfortable sending them to.
  • Supported documents: PDF with selectable text, .docx, .txt and .md.
  • Judge versions. ragevalkit pins its LiteLLM dependency to a tested range, so installs stay on versions that have been checked.
