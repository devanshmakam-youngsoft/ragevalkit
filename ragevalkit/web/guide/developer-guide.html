Is the new version really better?

ragevalkit replays your test questions through your own assistant, grades every answer, and tells you which version to ship. This guide walks you from the first run to a pipeline you can trust, with code you can copy at every step.

The story we will follow

Priya's team at Acme Shop has a support assistant called Sidekick. Last week they shipped version 2. Since then, customers write in that refund questions get half an answer. Was version 2 worse than version 1? Nobody can say: each person tried a few questions by hand and remembers something different.

By the end of this guide Sidekick has a test set, two measured versions, a clear winner, and a build that stops anyone shipping a worse one.

Priya, Acme Shop and Sidekick are made up, and the numbers are illustrative. The behaviour is real.

What ragevalkit does

You hand it a function. It does the repetitive, error-prone part of testing for you.

Your assistantragevalkit calls your function once per test question, in order, like a real user.
→
GradingAn AI judge scores each answer, and the text your pipeline retrieved. Text metrics run alongside.
→
VersionsEvery run is saved as a version, so you can see what improved and what broke.
→
The decisionA recommendation says which version to ship, and why.

Three words you will meet

JudgeThe graderAn AI model by default. It can also be your own function, or your own rubric.

Your first evaluation

Fifteen minutes from nothing to a scored version. Nothing to set up beyond Python and a key for the judge model.

Chapter 1

Priya decides not to argue about version 2 any more. The plan: write down ten questions customers really ask, run them through Sidekick, and look at the scores.

  1. Install 
    pip install git+https://github.com/devanshmakam-youngsoft/ragevalkit.git

    On Windows, run this from Git Bash if git is not on your PowerShell path.

  2. Give the judge a model

    The judge is an AI model that grades the answers. Put its key in a .env file next to your script and ragevalkit reads it. The default judge is a Groq model, so:

    # .env
GROQ_API_KEY=your-key-here

    Any LiteLLM provider works, and you can skip the AI judge entirely.

  3. Serve your function

    Create eval_entry.py next to your pipeline. Any function that turns a question into an answer works.

    import ragevalkit
from my_app import answer_question          # your existing pipeline

ragevalkit.serve(answer_question, port=8002, require_login=False)
    python eval_entry.py

    The dashboard opens at http://localhost:8002. Without require_login=False the sign-in is admin / admin123.

  4. Add test cases

    Open Test Cases and press + New test case. Write a question and what a good answer says. Ten is plenty to start. Later you can import a spreadsheet or have ragevalkit write cases from your own documents.

  5. Run it

    Press Execute session, name the version 1, choose your test cases and start. A progress bar follows each question.

  6. Read the result

    Open the version. You get an average score for answer quality and context quality, the response time, plain-language findings, and every question with its answer and the judge's reason.

What good looks like

Scores are out of 10. As a rule of thumb: 8 and up is strong, 5 to 7 is fair, under 5 means the answers are mostly wrong or missing. The numbers matter less than the change between versions, which is what the rest of this guide is about.

If every score is 0.0

Do not panic: the judge is usually right. It almost always means the test cases ask about things your pipeline does not know, so it answers “I could not find that”. Open one question, read the generated answer and the retrieved text, and compare them with what you expected. Troubleshooting has the details.

Chapter 1, continued

Version 1 of Sidekick scores 6.4 on answers. For the first time the team has a number. Refund questions score lowest, which matches what customers said. Next stop: connect Sidekick properly, so ragevalkit sees what it really does.

Connect your function

ragevalkit reads the parameter names of your function to decide what to pass. There are three shapes, and one of them is yours.

Chapter 2

Sidekick keeps each customer's chat on the server, keyed by a session id. That decides which shape Priya needs below.

The three shapes

Every question is answered on its own. The simplest shape, and right for single-turn pipelines.

Your chatbot is stateless: it rebuilds the prompt from the earlier turns every time. ragevalkit keeps the conversation of each chat_id and hands you the earlier turns as history (empty on the first turn).

Your backend is stateful: it remembers the conversation itself. ragevalkit passes one session id per chat, the same for every turn of that chat and different for the next. This is Sidekick.

How ragevalkit chooses

If a parameter is named…ragevalkit passes…
session_id, session, thread_id, conversation_id, user_idthe session id of the chat (shape 3)
history, chat_history, messages, conversation, turns, contextthe earlier turns (shape 2)
anything elsenothing: the first parameter is always the question

If a function has both kinds, the session id wins. Any other parameter needs a default value, because ragevalkit passes only the question and one extra.

Good to know

A parameter called context is treated as history. If yours means something else, rename it or list your own names with history_params=[…].

Other things your function can do

Return a dictionary or a Pydantic model, be async, use parameter names of your own, or receive the history as chat messages.

The keys tried for the answer, in order, are answer, response, output, result, text, content, message, generated_text, generation, completion. Add your own with answer_keys=[…].

If your function raises an error, that question is marked failed, the reason is recorded, and the run carries on with the next question.

LangChain, LangGraph and friends

Steps belong to the question being evaluated, not to the place they are written. Whichever node, thread or async task runs your code, the step lands in the right place.

LangGraph

Three placements work, and the example uses all three:

  • a node that calls a decorated function: the decorator records the call wherever it is made from;
  • a node with a with block inside it;
  • a decorator on the node itself, including nodes that take LangGraph's config parameter.

The version page then shows rewrite, retrieval and llm with their times, the retrieved text and the source refunds.pdf. Parallel branches and async nodes (ainvoke) are recorded too; we ran this file and variants of it while writing this guide.

Good to know

A LangGraph node returns a state update such as {"docs": […]}, so a decorated node with material=True would give the judge that dictionary as text. For the node that does retrieval, a with block lets you set clean material and sources.

Steps that run in parallel each report their own time, so together they can add up to more than the question's response time. That is expected.

LangChain

Steps work inside runnables, including the branches LangChain runs in parallel threads. In this chain a vector search and a keyword search run side by side, and a merge step declares the retrieved text once.

Anything else that runs in your process

LlamaIndex, Haystack, hand-written loops, thread pools: ragevalkit remembers one thing, which question is being evaluated, and attaches every step to it. You do not need to pass anything around. Your pipeline's own code does not change when you add steps.

Agents and bots with no retrieval

Not every assistant looks things up in documents. Tool-calling agents and greeters need a slightly different setup, and a different way to grade them.

An agent that calls tools in a loop

The model asks for a tool, gets the result, and decides again until it can answer. Two things are worth knowing:

  • A step that runs several times has its times added up. The llm step below runs once per loop, and the timing bar shows the total.
  • When the tool results are how the agent gets its facts, declare them as material. The judge then checks that the answer is supported by what the tools returned.

The tools_used note appears next to the question in the results, which makes it quick to see which tools a wrong answer relied on.

A bot with no retrieval

Greeting bots and small talk have no “retrieved context” to score. Tell ragevalkit, and they are graded on the answer alone.

  1. Mark the test cases non-rag (a type column when importing, or the type box on a test case). Their context quality is then left out instead of scored as 0.
  2. Do not declare material in these steps. Intent checks and tool calls are timing-only.
  3. Set material_weight=0, so the recommendation looks at answer quality only.
  4. Write the expected answer as a behaviour when exact words do not matter: “Greets the user politely and offers help”, “States that order A100 has shipped”. The judge grades the behaviour.
Tip

A mixed assistant, with both knowledge questions and small talk, is the common case. Keep one test set and mark each case rag or non-rag; each is graded the right way.

Plug into what you already have

You do not have to rewrite anything. Evaluate a bot that is already deployed, or keep production and evaluation side by side in one codebase.

A bot that is already deployed

No access to its code? Your function can simply call it over HTTP, and ragevalkit scores whatever comes back. This version uses only the standard library and passes the session id along, so multi-turn test cases keep their memory on the bot's side.

If the bot's API also returns the passages it used, put them in a with ragevalkit.step(…) block as s.material and s.sources and you get context scores too. If it does not, answer quality is still measured.

Production and evaluation, side by side

Your pipeline module keeps its step() and note() calls, which do nothing in production. Production imports the module as it always did, and a separate entry file serves it for evaluation.

Production — unchanged

The evaluation entry point

uvicorn production_app:app --port 8000     # production
python eval_entry.py                       # evaluation, only when you want it
Safe by default

For an extra guarantee, serve(..., eval_env="prod") turns the dashboard and every evaluation route off; only /api/health answers.

Why record steps?

A score tells you that an answer was wrong. Steps tell you where it went wrong, which is the part you can fix.

Chapter 3

Version 1 scores 6.4, and refund questions score lowest. Priya opens one of them: “Can I return an item, and when does the refund reach my account?” Sidekick answered only the second half. The answer is the symptom. To find the cause, Priya needs to see what happened inside.

What a step gives you

A step is a named stage of your pipeline: rewriting the question, searching, re-ranking, calling the model. Mark the stages and, for every question, the dashboard shows:

  • How long each step took: the “where the time goes” bar on the version page.
  • What was retrieved: the passages the judge scores as context quality.
  • Which documents were used: checked against the sources you expected.
  • Notes you attach: intent, tool called, difficulty… anything you want next to the question.

For Sidekick that means one look at the retrieved text shows the cause: the search returned the refund-timing passage and not the returns policy. The model did its best with what it was given.

A complete example

A typical RAG pipeline with four stages. Only the search declares what was retrieved; the others are timing only. The next pages explain why.

Nothing happens in production

Outside an evaluation, step() and note() record nothing and add almost no overhead, so the same code can ship. Arguments named like secrets are never stored.

There are two ways to write a step. They look similar and differ in what they record: that is the next page.

with or decorator?

Two ways to mark a step. They record the same name and time; the difference is in what else they keep, and that decides which one to use.

The same pipeline, both ways

Two steps, retrieval and llm, written first with with blocks and then with decorators. The helpers are identical.

With with blocks — you say what is recorded

With decorators — the function is the step

What each one records

Run the question “Can I get a refund?” through both and this is what the dashboard keeps:

Recorded for the stepwith blockDecorator
Step name and how long it tookyesyes
Material (the text the judge scores)what you assign to s.materialthe return value, when you write material=True
Sources (checked against expected_sources)what you assign to s.sourcesnot available: use a with block
Inputs of the stepnot recordedevery argument, by name
Output of the stepnot recordedthe return value
Coversany block, even part of a functionthe whole function

Which one should I use?

Use withFor retrieval, and for parts of functionsYou choose exactly what counts as material and sources, and you can wrap just a few lines.
Use a decoratorWhen a function is one clear stageInputs and output show up in the step details with no extra code, which helps when chasing a wrong answer.
Mix freelyOne pipeline can use bothA decorator on the model call, a with block on the search. They add up the same way.

The question people ask next is “does it still work if my decorated function is called from inside a LangGraph node?” It does: see LangChain, LangGraph and friends.

Material, sources and notes

Three small ideas that make the difference between a clear picture and a confusing one. The rule that matters most: declare each of them once.

Say which step retrieved the text

The judge reads only the steps that declare material: a with block that sets s.material, or a decorator with material=True. Steps that do not declare it are timing only, which is exactly what you want for a re-ranker or the model call.

Declare it once

If several steps set s.material, the judge reads all of them one after another: routing details, search settings and the context, sometimes the same context twice. Context quality then looks lower than the retrieval deserves, and the end can be cut off at the material limit. Let one step, the retrieval, declare the material. Put anything else you want to see in ragevalkit.note(…).

If no step declares anything, ragevalkit falls back to the output of decorated steps and writes a warning to the log that says how to be precise.

Sources

Sources are the names of the documents your retrieval used. Set s.sources = [...] in the retrieval step and ragevalkit compares them with the expected_sources of each test case (Source checks shows how). The sources of every step are put together, each document once, so report them in the retrieval step only.

Decorators cannot report sources. Use a with block for the step that retrieves.

Notes

ragevalkit.note("intent", "billing") attaches a short fact to the question being evaluated. It appears beside the question in the results, so you can see at a glance which intent or tool a wrong answer went through. Names such as password, token or api_key are never stored.

How much is recorded

OptionEffect
record_detail="all" (default)name, time, inputs, output, material and sources for every step
record_detail="selected"only steps that set material or sources yourself
record_detail="off"step names and times only
record_mode="off"no steps at all; the evaluation itself still runs
step_value_chars (1000)how much of a step's inputs, outputs and notes is shown; longer values end with a marker saying how much was left out
material_chars (20000)how much retrieved text the judge reads per question

A long list of numbers, such as an embedding, is shown as [1536 numbers] instead of being stored.

Writing test cases

A test case is a question, what a good answer says, and where it sits in a conversation. A small, honest set beats a large careless one.

Chapter 4

Priya reads the last month of support chats and picks twelve real questions: five about refunds, three about shipping, two follow-ups that only make sense after the first answer, and two greetings.

The columns

ColumnMeaning
questionThe only column you must have.
expected_answerWhat a good answer says. Wording can differ; the judge compares meaning.
chat_id, turn_noCases with the same chat_id form one conversation, replayed in turn_no order. Leave them out and every question is its own chat.
typerag (default: the answer comes from your documents) or non-rag (greetings, small talk, tools: graded on the answer only).
expected_sourcesDocuments the pipeline should retrieve. See Source checks.
groupsLabels, for example Billing; Refunds. A case can carry any number of groups.

A sample file

Five test cases in a CSV. You can import this exact file from Test Cases → Import; you see a preview before anything is saved.

  • refund-1 is a two-turn conversation: both rows share a chat_id and are replayed in turn_no order. The second question only makes sense after the first.
  • Row 3 needs both documents (|); row 4 accepts either one (,, in quotes because the cell contains a comma).
  • hello-1 is non-rag, and its expected answer is a behaviour, not exact words.
  • The groups column creates the groups Billing, Shipping and Small talk.

Writing good ones

  • Use real questions, in the words customers use. Rewriting them to be tidier makes them easier than reality.
  • State the facts the answer must contain, not a full model answer. “Within 30 days of purchase” is better than a paragraph.
  • Include the awkward ones: follow-ups, questions with two parts, questions your documents do not answer. The last kind should expect an honest “I don’t know”.
  • Keep them stable. A case counts as the same across versions only while its question and expected answer are unchanged. Edit one and it starts a new history, which the comparison will tell you about.

Import, generate and organise

Four ways to fill the test set, and groups to keep it tidy. Use whichever fits the day.

Four ways to add test cases

One at a time+ New test caseFor the question you just thought of.
From a spreadsheetImportExcel, CSV, or rows pasted from a sheet.
From your documentsGenerate from documentsragevalkit writes questions, with the evidence for each answer.
From a scriptThe APIFor test cases kept in a repository: POST /api/test-cases/import. See Run it in CI.

Importing

  • You see what will be added, updated or skipped before anything is saved, with the row number and reason for every row that cannot be used.
  • Only the question column is required. Common header names (query, gold_answer, tags…) are recognised, and you can point any column at the right field.
  • Safe to repeat: importing the same file twice changes nothing; an edited answer becomes a new version of the existing case.
  • Rows that could not be imported can be downloaded with the reason next to each, fixed, and imported again.
  • Your own column names everywhere? column_map={"user_query": "question", "gold_answer": "expected_answer"} in serve().

Generating from documents

Test Cases → Generate from documents writes questions from your PDF, Word, text or Markdown files (up to 5 files of 50 MB). By default it writes three questions in each of four categories:

CategoryWhat it is
DirectThe answer is stated plainly in one place.
IndirectThe answer is in the document, but the question uses everyday words rather than the document's own.
Multi-partOne question with several parts, answered from different places.
Multi-turnA short conversation. Each follow-up depends on the earlier answer and cannot be understood alone.
  • Every answer comes with evidence: the sentences of your document that prove it, with file and page.
  • Nothing is added until you press Add. Questions are saved while they are being written, so closing the browser loses nothing, and you can edit or remove any of them first.
  • Nothing of the upload is kept, only the questions, answers and evidence snippets.
  • The text of the documents goes to the model you set with generator_model (the judge model by default). A local ollama/… model keeps it on your machine.
Tip

Generated questions are about your documents. Make sure your pipeline has those same documents loaded, or every score will be 0, and rightly so.

Groups

A group is a label. A case can carry any number of labels, and you add or remove them from the Test Cases page. Use them to run a slice (“only Billing”) and to see scores per slice on the version page. When you run several groups, a case in two of them runs once.

Follow-up questions need the turns before them, so by default a run also includes the earlier turns of every case you picked. The Execute dialog shows exactly how many cases will run, and lets you turn that off.

Deleting: a test case is removed for good (past versions keep their own copy of the question and answer, marked “Test case deleted”). A group is only hidden and can be restored. To keep a case but skip it in runs, mark it inactive.

Source checks

Right answer from the wrong document is luck. Source checks confirm that the documents you expected were the ones retrieved.

How it works

  1. The pipeline reports its sources

    In the retrieval step, s.sources = [...] lists the documents it used.

  2. The test case lists the expected ones

    In the expected_sources column, with two small rules below.

  3. ragevalkit compares them

    Each question shows what was found and what is missing, and the version page counts them.

The two rules

You writeIt means
refunds.pdfthat document must be retrieved
shipping.pdf | tracking.pdfboth are needed (| means AND)
tracking.pdf , tracking_v2.pdfeither is enough (, means OR)
a.pdf , a_v2.pdf | policy.pdf(a or a_v2) and policy

Two ways to compare names

source_check_modeBehaviour
"keyword" (default)Fast and predictable. Ignores case, folders and file extensions, so docs/Refunds.PDF matches refunds.
"llm"Asks the judge model, which also copes with different spellings of a name. Adds a score and a short comment.
"off"No source checking.
If sources say “not checked”

Either the test case has no expected_sources, the mode is "off", or no step reported sources. Remember that decorators cannot report sources. Troubleshooting has the full list.

Reading the results

Every number on the version page, in plain words, and where to look when one of them surprises you.

The scores

You seeIt means
Answer quality (0–10)The judge compares the answer with your expected answer, for facts and intent.
Context quality (0–10)Did the retrieved text contain what was needed to answer? Left out for non-rag cases.
Response time and the step barFrom question to final answer, and how that time splits across your steps.
Key words, wording, meaningText metrics that need no AI: shared key words, similar phrasing (BM25), similar meaning (sentence embeddings).
Score tiersHow many questions were strong (8–10), fair (5–7) or weak (0–4).

Watch-outs and suggestions

At the end of each run the judge model writes plain-language findings: each thing to look at, paired with the next step to try. They name the group or question and use the numbers as evidence, rather than repeating the headline scores. Change what they look for with summary_prompt (Your judge).

One question at a time

Click any row to open that question: the answer, the expected answer, the judge's reason for each score, the retrieved text, the sources found and missing, the time per step, and your notes. This is where wrong answers get explained.

  • Filter by group or score tier, and sort by score or time.
  • A question whose test case has been deleted since is marked, and keeps its own copy of the text.
  • Download an Excel report from the version page: a summary sheet, and one row per question.

Problems during the run

If something went wrong, the version page lists it in plain words, with Show technical details for the error and Download log for the full story. The same problem on many questions is listed once with a count. While a run is going you see a live count.

  • A failing pipeline function never stops a run: that question is marked failed, the reason is recorded, and the run goes on.
  • Logs are in eval_logs/ next to your results file: server.log, one file per run, one per generation. Keys and passwords are hidden before anything is written.
Tip

Read Problems during this run before the scores. A run where half the questions failed has misleading averages.

Comparing versions and choosing one

The point of all this. How ragevalkit compares versions fairly, what the recommendation card is telling you, and when it deliberately says nothing.

Chapter 5

Priya makes one change to Sidekick: the search now reads three passages instead of one. Same test cases, run again as version 2. The refund question that only got half an answer now gets both halves. The dashboard has to say whether that is really better, and it has to be right.

Change one thing, run again

That loop is the whole product: change something, restart, run the same test cases under a new version name. This example reads its search depth from an environment variable, so the same file is both versions.

python versions_workflow.py              # run it as version 1: one passage per question
TOP_K=3 python versions_workflow.py      # run it as version 2: three passages per question

On Windows PowerShell set the variable first: $env:TOP_K = 3. Everything else about the version, its notes and its groups, is saved with the run.

How versions are compared

An average is only fair when the versions answered the same questions. So ragevalkit compares them on the test cases they all ran:

  1. A case counts as the same only if its chat, turn, question and expected answer are unchanged.
  2. Adding a test case, or running an extra group, in a later version does not hide that version: it is judged on the cases the others also ran, and the card says so.
  3. If the shared cases are only a thin slice (say a 2-question smoke test next to 10-question runs), that version is left out and the reason is shown, so it cannot shrink everyone else's comparison.
  4. Versions that were stopped early, or failed on a shared case, are left out too.
  5. Each remaining version gets an overall score: answer quality and context quality, weighted 60/40 by default. If context quality was not graded for every version, all are compared on answer quality alone, and the card says so.
  6. Versions within a small tolerance (0.25 by default) of the best are tied, and the fastest of them wins.

What the card is telling you

The card saysWhat it means, and what to do
Recommended: v2 and the reasonThe best overall score among comparable versions; if several are tied, the fastest. Safe to ship on the evidence you have.
None yet, “Best so far: v1”No version reaches the minimum score of 5 out of 10, so nothing is recommended, but the best so far is named. A version that mostly gets answers wrong is not something to ship. Improve the pipeline, or check that the test cases ask about what it knows. Change the bar with recommendation_min_quality.
Latest v3 vs v2: answer −0.4 · context +0.1 · 1.2s slowerYour newest run against the recommended one, on the shared cases. It answers “should I ship what I just built, or stay on the pick?”.
“The latest run moved the recommendation from v1 to v2”Before the newest run, v1 was the pick. This run changed that.
Not compared: v3 (answer 10.0, context 10.0) ran 2 test cases and shares only 0…That version ran different test cases (typically because cases were edited, added or deleted), so it cannot be ranked against the others. Its own scores are shown so a good one is not hidden. Run the same test cases on both versions to compare them.
Left out: v4, 3 of the 6 shared test cases failedA version with failures on shared cases would look better or worse than it is. Open it, fix what failed, run it again.
“No version responds within 8s”You set a response-time ceiling and nothing meets it. The fastest is named.

Tuning the decision

OptionDefaultUse it to…
answer_weight / material_weight0.6 / 0.4decide how much answer quality and context quality count. Set material_weight=0 for assistants with no retrieval.
recommendation_tolerance0.25widen or narrow what counts as a tie. A wider tolerance favours speed.
recommendation_min_quality5.0raise the bar for what may be recommended at all.
max_response_timenonenever recommend a version slower than this many seconds.

The card also has two boxes to try tolerance and a time ceiling on the spot, without restarting. Archive a version to take it out of every comparison without deleting it; the recommendation updates straight away. It is calculated on each visit from the saved scores, so it can never be out of date.

Groups work the same way: pick a group on the dashboard to see which version is best for that group, which is how you notice that v2 is better at refunds but worse at shipping.

Version 2 scores 8.1 against 6.4, in 0.4 seconds more. The card recommends it and shows the change since version 1. Priya ships version 2 with a number to point at, not a feeling.

Your own judge

Three levels, from a different model to no AI at all. Pick the lightest one that does the job.

Chapter 6

The product manager has a point: Sidekick is accurate now, but sometimes curt, and it promises refunds the policy does not allow. The default judge does not know that matters. Priya teaches it.

Level 1Another modelOne setting. Level 2Your own rubricThe AI judge, grading your way. Level 3Your own functionExact checks, no AI.

Level 1: another model

judge_model takes any LiteLLM model name, with its key in .env or judge_api_key=: "openai/gpt-4o-mini", "gemini/gemini-1.5-pro", "groq/llama-3.3-70b-versatile", "ollama/llama3". A fast model is a good choice while you iterate: every question makes at least one judge call.

Level 2: your own rubric

Keep the AI judge but tell it how your answers should be graded. Describe only the grading: ragevalkit adds the reply format itself, so a custom rubric cannot break the reply. summary_prompt does the same for the written findings.

Level 3: your own function

For exact checks, rules, a JSON schema, or your own scoring service, replace the AI judge with a function. It receives the question, the expected answer, the generated answer and the retrieved material, and returns answer_marks (0–10) with an optional comment, plus material_marks if you grade the context too.

Good to know

The written findings at the end of a run are produced by the judge model, even when you use judge_fn. Without a key for it the run still finishes, and the version says the findings could not be written.

Setting it up for a team

Accounts, where things are kept, which models, and how the recommendation decides. One file, with the reason for each line.

Chapter 7

Sidekick's evaluation was running on Priya's laptop. Now the whole team wants to use it, and the results should survive a laptop reboot.

The parts that matter

  • Sign-in. users="alice:pw1,bob:pw2" sets the accounts. Sessions last 12 hours; set secret= to a fixed value if people should stay signed in across restarts. require_login=False skips the sign-in for local work.
  • Data. Everything is in one JSON file (store_path, default eval_store.json). Copy it to back it up or move it to another machine.
  • Logs. eval_logs/ sits beside it: server.log, one file per run, one per generation, each with full details. log_dir= moves them, for example onto a mounted volume. Keys and passwords are hidden before anything is written.
  • Where it listens. The server is reachable on this computer (127.0.0.1). To share it, run it on a shared machine behind your usual network setup, with sign-in on.
  • Production safety. eval_env="prod" turns the dashboard and every evaluation route off; only /api/health answers.
  • This guide. It is on by default. show_guide=False hides the Help link and stops serving it.
  • Pin the version. Install by tag in requirements.txt (…ragevalkit.git@<tag>), so everyone evaluates with the same code.
Tip

Give every release its own version name and run the same test cases each time. The comparison is only as good as the consistency of the test set.

Run it in CI

Keep a ragevalkit server running, let every build ask it for a score, and fail the build when quality drops.

Chapter 7, continued

Two weeks later someone changes the prompt and refund answers get worse. Nobody notices until customers do. Priya adds a gate: no merge unless the Billing group scores at least 7.5.

The script

It talks to the same API the dashboard uses, with only the standard library. It starts a run for a group of test cases, waits for the version to appear, and exits with a code your CI understands.

EVAL_URL=http://eval-server:8002 EVAL_GROUP=Billing EVAL_MINIMUM=7.5 python ci_gate.py
Exit codeMeaning
0answer quality reached the bar and no question failed
1below the bar, or at least one question failed
2no result within the wait time: look at the dashboard or at eval_logs/

Settings it reads

  • EVAL_URL: where the server is. EVAL_USER and EVAL_PASSWORD are needed only when sign-in is on.
  • EVAL_GROUP: the group of test cases to run. EVAL_MINIMUM: the answer quality the build needs.
  • EVAL_VERSION: the name of the version it creates (by default ci- and the date and time).
Good to know

Each CI run is saved as a version, so the dashboard shows how quality moves build by build. Archive old CI versions to keep comparisons tidy.

The API is browsable at /api/docs on your server, and you can import test cases the same way with POST /api/test-cases/import.

When you need help

When something looks off

Find your symptom, see the likely reason, and what to do about it. Most things here take a minute to fix.

Start with the Problems during this run box on the version page: it says what went wrong in plain words, and Show technical details gives the error. The full log is the Download log button, or eval_logs/runs/. Then look for your symptom here.

Every score is 0.0, but nothing failed

The judge is almost always right here: the test cases ask about things your pipeline does not know (for example questions generated from other documents), so it answers “I could not find that” and there is no retrieved text.

Do: open one question and compare the generated answer, the retrieved text and the expected answer. Load the same documents the test cases came from, or write test cases about what your pipeline knows.

The dashboard says “None yet” under Recommended version

No version reaches the minimum overall score (5 out of 10 by default), so nothing is recommended; the best so far is named. See Comparing versions.

Do: improve the pipeline and run again, or check the test cases. If 5 is the wrong bar for you, set recommendation_min_quality.

A version says “Not compared”

It ran different test cases from the others (cases were edited, added or deleted), so there is nothing fair to compare. A case only counts as the same while its question and expected answer are unchanged.

Do: run the same test cases on the versions you want to compare. The card shows the not-compared version’s own scores so a good one is not hidden.

Every question says “No answer: the assistant returned an error”

Your function raised an error. The run itself is fine: ragevalkit marks the question failed, records why, and carries on.

Do: open Problems during this run and Show technical details; the last lines name the error. Call your function by hand with one of the questions. Common causes: a key your own pipeline needs is missing from .env, a file path that only works from another folder, the vector index was not loaded before serve() (load it first, as your app does at start-up), or the function needs a second argument that has no default.

“The question was answered, but the AI judge could not grade it”

The judge model did not answer. The usual reasons are shown in the message: a missing or wrong API key, a model name that does not exist, a rate limit, or no network.

Do: put the provider’s key in .env (GROQ_API_KEY, OPENAI_API_KEY…) or pass judge_api_key=; write the model as provider/model; for a rate limit, wait a minute or run fewer questions. Or use your own judge function, which needs no model.

“The AI could not write the findings for this run”

The findings come from the judge model, even when you use judge_fn.

Do: the same checks as above (key, model name, network). The scores and every answer are saved; only the written findings are missing.

Context quality is blank or very low

No step declared the retrieved text, or the case type says no retrieval is expected.

Do: in your retrieval step set s.material = … (or use @ragevalkit.step("retrieval", material=True)). If the bot has no retrieval, mark the cases non-rag and use material_weight=0. See Say which step retrieved the text.

Context quality is lower than the retrieval deserves

More than one step declares material, so the judge reads routing details, search settings or the same text twice, and the end can be cut off at material_chars.

Do: open a question’s Retrieved text and check it holds only the passages. Let one step declare the material; keep the other steps timing-only and put their details in ragevalkit.note().

The step-time bar only shows “Not in a step”

No step ran during the questions, or recording was reduced.

Do: check that your pipeline calls ragevalkit.step(…) on the path the questions take; check record_mode is not "off"; with record_detail="selected" only steps that set material or sources are kept.

Step times add up to more than the response time

One step sits inside another (the outer one includes the inner one’s time), or steps run in parallel.

Do: for nesting, make the steps follow each other instead of wrapping each other. Parallel steps are expected to overlap.

Sources say “not checked”, or “some missing” when they were found

Not checked: the test case has no expected_sources, source_check_mode is "off", or no step reported sources. Missing although retrieved: the names differ.

Do: report sources with a with block and s.sources = […] (decorators cannot report them). Compare the names the step reported with expected_sources; the keyword check ignores case, folders and file extensions, so docs/Refunds.pdf matches refunds. Different spellings of the same document? Try source_check_mode="llm".

A step shows no inputs or output

Inputs and outputs are recorded only for decorated functions.

Do: use the decorator for that step, or record what you need with ragevalkit.note(). Arguments named like secrets show as [REDACTED] on purpose.

“Another evaluation is already running”

One evaluation runs at a time.

Do: wait for it, or press Stop on the version in progress; a stopped run keeps its partial results.

“Version … already exists” or “Version may only contain letters, digits…”

Version names are unique, and use letters, digits, ., _ or - (up to 20 characters).

Do: choose a new name, or tick the option to replace the existing version.

“No runnable test cases in the selection”

The groups you picked are empty, or their cases are all inactive.

Do: add cases to the group, or mark them active. The Execute dialog shows how many cases will run before you start.

A function with a parameter called context or user_id gets the wrong thing

Those names are on the lists ragevalkit uses to recognise history and session parameters.

Do: rename the parameter, or set history_params=[…] and session_params=[…] to your own names. See Connect your function.

The answer shows as a dictionary or object text instead of the answer

Your function returned a dictionary or object, and none of its keys is a known answer key.

Do: return a string, or add your key with answer_keys=["my_key"].

I cannot sign in, or I am signed out after a restart

The default account is admin / admin123 unless you set users=. Without a fixed secret= a new one is made on every start, which ends existing sessions.

Do: set users= and secret=, or require_login=False locally.

“Missing required column(s)” when importing

The file does not have the columns the older dataset upload needs.

Do: use Test Cases → Import, which only needs a question column and lets you pick which column is which; or add column_map= to serve().

Generating test cases: “has no selectable text”, “password-protected” or “old Word files”

The file cannot be read as text: a scanned PDF, a protected file, or a .doc.

Do: upload a text-based PDF, remove the password, or save .doc files as .docx. Plain .txt and .md always work.

The dashboard looks old after an update, or a new option is not recognised

The environment still has the previous version of ragevalkit, or the browser kept the old page.

Do: reinstall with pip install --force-reinstall --no-deps git+https://github.com/devanshmakam-youngsoft/ragevalkit.git, then refresh the page with Ctrl+F5.

“Address already in use”, or the page does not open

Another program is using the port, or the browser did not start.

Do: pick another one with port=8003 and open http://localhost:8003 yourself.

“Semantic similarity failed” in the problems list

The small local model for the “meaning” score could not load, usually the first time on a machine with no internet.

Do: connect once so it can download, or set run_semantic_similarity=False. All other scores are unaffected.

Where are the logs, and what should I send when asking for help?

Do: on the version page press Download log, or open eval_logs/runs/ next to your eval_store.json. For an error outside a run (a message with a reference number), search eval_logs/server.log for that reference. Keys and passwords are already hidden.

Every option with its default, grouped by what it is for. Only fn is required.

Your function

ParameterDefaultWhat it does
fnrequired

Your pipeline function. Accepted signatures::

fn(question: str) -> str
fn(question: str, history: list) -> str   # stateless, runner passes history
fn(question: str, session_id: str) -> str # stateful, you manage history

Can also return a dict (ragevalkit extracts the answer via answer_keys) or a Pydantic model. Async functions are supported.

Server

ParameterDefaultWhat it does
port8001

HTTP port for the server. Default 8001.

store_path"eval_store.json"

Path to the TinyDB JSON results file. Created automatically.

log_dirNone

Folder for log files. Default: eval_logs next to store_path. It holds server.log and one file per evaluation run (runs/) and per test case generation (generation/), with full tracebacks.

log_level"INFO"

Level of server.log and the console ("INFO" by default; "DEBUG" for more).

Show the guide on the dashboard's Help page (default True). With False the Help link is hidden and the guide is not served.

open_browserTrue

Open the dashboard in a browser 1.5 s after startup.

Environment / recording modes

ParameterDefaultWhat it does
eval_env"dev"

Environment mode. "dev" (default) enables the full dashboard. "prod" blocks the dashboard and all eval routes — only /api/health responds, suitable for embedding the function behind a production server without exposing the eval UI. "uat" is like dev but logs that UAT recording is active.

record_mode"eval"

Controls when @ragevalkit.step() fires. "eval" (default) records steps only during eval runner calls. "off" disables step recording entirely even during eval (eval still runs, just no step data).

record_detail"all"

Controls how much detail each step captures. "all" (default) records inputs, outputs, material, sources, and timing. "selected" records only steps where the developer explicitly set .material or .sources. "off" records only step name and elapsed time.

max_step_value_chars1000

How much of a step's inputs, output and note() values is kept for display (default 1000). A longer value ends with "… (+N more characters)"; a long list of numbers, such as an embedding, is shown as [N numbers].

max_material_chars20000

How much retrieved text the judge reads per question (default 20000), cut with the same kind of marker. Material comes from steps that declare it (s.material = … or @step("retrieval", material=True)).

ParameterDefaultWhat it does
judge_model"groq/openai/gpt-oss-120b"

LiteLLM model string. Examples: "groq/llama-3.3-70b-versatile", "gemini/gemini-1.5-pro", "openai/gpt-4o", "ollama/llama3".

judge_api_keyNone

Explicit API key for the judge. If omitted, LiteLLM reads the matching env var (GROQ_API_KEY, GEMINI_API_KEY, OPENAI_API_KEY…).

judge_promptNone

Custom system prompt for the grader. Replaces the built-in rubric entirely — useful for non-RAG systems (customer support, coding assistants…).

judge_retries3

Retries on transient LLM failures before the row is marked failed.

Callable that fully replaces the LLM judge::

def my_judge(question, expected, generated, material) -> dict:

ParameterDefaultWhat it does

How to verify retrieved sources against expected_sources in the dataset. Returns the session ID for a given chat_id. Defaults to uuid.uuid4(). Supply a deterministic function to replay conversations with the same session against a stateful backend::

Good to know

  • One evaluation runs at a time. Finished results are saved as they complete. A run in progress lives in the running server, so if the server restarts, start that version again.
  • Documents sent to a model. Generating test cases sends the text of your documents to generator_model (the judge model by default). Choose one you are comfortable sending them to.
  • Supported documents: PDF with selectable text, .docx, .txt and .md.
  • Judge versions. ragevalkit pins its LiteLLM dependency to a tested range, so installs stay on versions that have been checked.
  • The API. Everything the dashboard does is a call to /api/… on the same server; the interactive reference is at /api/docs.
